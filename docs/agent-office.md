# Agent Office — концепт (v0.1)

Веб-офис с агентами-сотрудниками: каждый матч обрабатывается своим агентом,
несколько матчей — параллельно, сверху один «генерал», с которым общается оператор.

Статус: **концепт, к реализации не приступали.**

## 2. Диагноз: почему текущий агент отвечает «нет данных»

Разбор удалённого кода (`git show cbbf8a5~1:backend/src/ai/...`):

1. Бриф собирался из состояния БД **на момент формирования промпта**
   (`buildDecisionBrief` → `matchup.build()`), а не по запросу «дай свежее».
2. Системный промпт прямо задавал смещение: *«a pre-computed decision brief so the
   agent almost never NEEDS a tool call for the common case»* + правило
   *«используй инструменты, если не хватает данных»*. Модель видит `n/a` и
   спокойно возвращает `pass` с формулировкой «данных нет».
3. **У агента физически не было инструмента, который делает live-fetch.**
   Единственный «перепроверить» — `eval_game`, а он вызывает тот же
   `matchup.build(gameId)` → те же строки в БД. Даже если модель послушно
   вызвала бы инструмент, ответ был бы идентичным.

Отсюда и «он говорит нет»: не лень модели, а отсутствие пути к свежим данным и
промпт, который разрешал не искать.

**Вывод, определяющий всю архитектуру:** данные должны **приезжать вместе с
задачей**. Агент не ходит за фактами никогда. За свежесть отвечает backend.

## 3. Три роли

```
                    ┌─────────────────────────────────────┐
   оператор ───────▶│  ГЕНЕРАЛ (супервизор, чат)          │
                    │  tools: только оркестрация          │
                    └──────────────┬──────────────────────┘
                                   │ enqueue / retry / отчёт
                    ┌──────────────▼──────────────────────┐
                    │  BACKEND — оркестратор и факты      │
                    │  pipeline → pack → fingerprint →    │
                    │  AgentTask (idempotent, priority)   │
                    └──────────────┬──────────────────────┘
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        ┌──────────┐         ┌──────────┐         ┌──────────┐
        │ ВОРКЕР   │         │ ВОРКЕР   │         │ ВОРКЕР   │
        │ LAD@SF   │         │ NYY@BOS  │         │ CHC@MIL  │
        │ prematch │         │ inn1     │         │ prematch │
        └──────────┘         └──────────┘         └──────────┘
         вход: pack + candidates + FormulaSpec   выход: decision JSON
```

### 3.1 Backend — владеет фактами и календарём

- Крутит стадии как сейчас (live 30s, stage_watch 60s, prematch/context 2m, slate 10m).
- Считает **fingerprint контекста** матча (состав, SP, судья, погода, версия формулы)
  и **packHash** (fingerprint + линия + стадия).
- Создаёт `AgentTask` только тогда, когда пак **полон для своей стадии**.
- При изменении fingerprint — новый таск с версией, старый помечается `superseded`.
- Сам матан НЕ отдаёт LLM: λ/вероятности/value считает скрипт, агенту приходят
  **готовые кандидаты** (signals/value_bets) — как в правиле №1 старого
  `DECISION_SYSTEM_PROMPT`.

### 3.2 Воркер — одно действие, один матч, одна стадия

| | |
|---|---|
| Вход | pack (с `as_of`) + precomputed candidates + FormulaSpec |
| Инструменты | **нет** (опционально один — `record_decision`) |
| Раундов LLM | 1 (сейчас до 6 с растущим контекстом) |
| Выход | `{action, market, side, line, model_prob, value_pct, confidence_tier, rationale, notify_brief, risk_flags}` |
| Инвариант | ставить можно **только** на линию из `signals`/`value_bets`; иначе отказ валидатора → `pass` |
| Таймаут | N сек → таск возвращается в очередь с backoff |

Зон ответственности ровно одна: «применить формулу к замороженному пакету».
Никакого «сначала понять задачу, потом получить данные, потом вспомнить формулу».

**Почему одновременные старты больше не проблема:** воркеры независимы, у каждого
свой пакет и свой контекст. Конкурентность ограничивается лимитом, порядок —
приоритетом по времени старта матча (матч через 20 мин важнее матча через 3 часа).

### 3.3 Генерал — то, с чем разговаривает оператор

Инструменты — **не** данные, а оркестрация:

```
list_tasks(filter)          get_task_result(task_id)
list_workers()              explain_decision(task_id)   ← читает трейс
enqueue_task(game, track)   cancel_task / retry_task
pause_schedule / resume     run_slate_now
get_ledger_stats(days)      list_escalations()
```

Он видит: сколько воркеров работает, кто на каком этапе, кто упал, какие решения
приняты и почему. Он **не считает формулу и не ходит за данными** — за него это
делают backend и воркеры.

### 3.4 Эскалация в Гермес (важно)

Воркер — быстрый и дешёвый, покрывает ~90% случаев. Если:

- воркер упал K раз,
- пак пришёл с большим числом `default` в `input_sources`,
- генерал пометил матч как нестандартный,

→ задача эскалируется в **полноценную сессию Hermes** со скиллами
`platewire-desk` + `platewire-f5-engine` + `platewire-pack`. Там уже можно
глубже копать. Так «тупые» воркеры и «умный» Гермес не конфликтуют, а
разделяют работу по цене/сложности.

## 4. Ключевые механики

### 4.1 Task как единица работы

```
AgentTask {
  id, gameId, track ('prematch'|'inn1'|'inn2'),
  packHash,            // версия входных данных
  supersedesId?,       // предыдущая версия (fingerprint изменился)
  status,              // queued|running|done|failed|superseded|escalated
  priority,            // по времени старта матча
  deadlineUtc,         // = game start (или конец иннинга для inn1/inn2)
  attempt, workerId?,  createdAt, startedAt?, finishedAt?
}
```

Идемпотентность: уникальность по `(gameId, track, packHash)`. Один и тот же пакет
не может породить две задачи.

### 4.2 «Пинаем агента при изменениях»

Это то, что ты описывал в переписке. Механика:

1. Стадия наступила (`stagesNeedingFreshCapture`) → пак собран → таск.
2. Линия/состав/SP изменились до принятия решения → fingerprint изменился →
   packHash новый → новый таск, старый `superseded`, его решение помечается
   `stale` (в аудите остаётся, в ledger не идёт).
3. Решение принято → `lock` → повторные таски по этому треку не создаются.

### 4.3 Жёсткое правило свежести

Backend **не создаёт таск**, если `as_of` пакета старше дедлайна стадии — вместо
этого он повторяет сбор. Именно это закрывает твой пункт «потерь не будет: инфа
фиксированная и актуальна на момент генерации».

### 4.4 Аудит

Возвращаем `AiDecisionTrace` (был в коде): `packSnapshotJson`, `promptJson`,
`rawOutputJson`, `model`, `latencyMs`. Каждое решение воспроизводимо: видно
ровно те цифры, которые видел агент.

## 5. Веб-офис (UI)

Новый раздел `/office` — витрина поверх оркестрации. Не замена текущему UI, а
третий экран рядом с «Матчи» и «Архив».

**Раскладка — «open space»:**

```
┌── ПОЛ ──────────────┬── LIVE FEED ─────────────────────┐
│ [LAD@SF]  аналитик  │ 14:02:11  enqueue task #a41       │
│  ● работает         │ 14:02:12  pack ok (as_of 14:02:09)│
│  prematch · 3с      │ 14:02:14  λh=2.31 λa=1.87         │
│  ─────────────────  │ 14:02:15  candidates: 2 signals   │
│ [NYY@BOS] ● ждёт    │ 14:02:17  ⚖ BET over 5.5 @1.92    │
│  причина: lineup    │ 14:02:17  trace #7f2 written      │
│  ─────────────────  ├──────────────────────────────────┤
│ [CHC@MIL] ● решено  │  ЧАТ С ГЕНЕРАЛОМ                  │
│  PASS · нет edge    │  «как дела по слайту?»            │
│ [SEA@HOU] ✕ ошибка  │  «3 в работе, 1 PASS, 1 ошибка —  │
│  retry 2/3 → эскал. │   lineup не пришёл, ретраю…»      │
└─────────────────────┴──────────────────────────────────┘
```

Комнаты-статусы: **Queued / Working / Waiting (данные неполные) / Done /
Failed & Escalated**. Клик по воркеру → его карточка с полным трейсом: пак,
λ, кандидаты, промпт, сырой ответ, финальное решение.

Отдельная панель: **«Почему PASS»** — по каждому отказу одна строка. Это снимает
главную боль «он говорит нет данных»: отказ всегда с причиной
(`no_signals` / `defaults_heavy` / `line_moved` / `not_ready`), а не «нет».

Стилистически это тёмный «торговый зал»: моно-цифры, плотные таблицы, статусные
точки, ноль декора. Живой лог — через SSE/WebSocket (в проекте уже есть
`socket.io-client` в зависимостях).

## 6. Деньги

Считаем по реальному расходу, а не на глаз.

| Позиция | Сейчас | В офисе |
|---|---|---|
| LLM-вызовов на 1 решение | до 6 раундов, контекст растёт | **1** вызов, плоский контекст |
| Токенов на решение | ~30–60k (растущий диалог + тулы) | ~8–12k (пак + кандидаты) |
| Решений в день (15 игр × 3 трека) | до 45 | до 45 |
| Курация формулы | 1/день + бэктест | без изменений (локальный счёт) |

Итого: **5–10× меньше токенов на то же число решений**, при полном сохранении
объёма. Плюс воркеров можно вести дешёвой моделью (структурный JSON), а дорогую
оставить генералу и куратору — сейчас `glm-5.2:cloud` стоит и на решении, и на
чате.

Ориентир: ~15–20M токенов/мес. На дешёвой модели — единицы долларов, на
премиальной — десятки. То есть **бюджет не является ограничением** — ограничением
была недетерминированность цепочки.

## 9. Открытый вопрос

Чем является воркер технически:

- **A. Сессией Hermes на задачу** (`hermes chat -s platewire-f5-engine -q <бриф>`).
  Плюс: переиспользуем скиллы, полный аудит. Минус: спавн процесса, тяжёлый,
  сложно стримить в UI, дорого на 45 задач/день.
- **B. Лёгким вызовом модели внутри Nest** (промпт из git, `tools: none`,
  ответ по схеме). Плюс: быстро, дёшево, стримится, детерминированно. Минус: логику
  воркера надо держать в бэкенде.
- **A+B (предлагается).** 90% матчей — воркер B. Эскалация, курация формулы и
  чат генерала — Hermes A. Быстро там, где рутина; умно там, где надо думать.

## 10. Инварианты (не нарушать)

1. Агент никогда не ходит за фактами — факты приезжают с задачей.
2. Математику считает код. LLM только выбирает из посчитанных кандидатов.
3. Одна задача — один матч — одна стадия.
4. Нет полного пакета — нет задачи (вместо «решить на пустых данных»).
5. Изменение данных → новая версия задачи, старая становится `superseded`.
6. Каждое решение имеет трейс с тем же пакетом, что видел агент.
7. Формулу активирует человек. Агент только предлагает.
